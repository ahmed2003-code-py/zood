# ADR 0005: Identifiers

**Status:** Accepted, 2026-11-12
**Source:** `docs/architecture/implementation-plan.md` §4, decision 5

## Context
Offline POS devices create records before they can reach the server, so ids cannot come only from a central sequence. Idempotency relies on a client-generated `clientTxnId`. People also need short references they can read out loud, such as on a receipt.

## Decision
- Primary keys are UUIDv7 (RFC 9562), generated by our own small `UuidV7` class in `platform.ids` (no extra library), behind an injectable `IdGenerator`.
- Short human-readable references (for example receipt references) come from database sequences.

## Consequences
- A device can create an id offline with no coordination and no clash.
- UUIDv7 is time-ordered, so it indexes well, unlike random UUIDs.
- Receipt references and later invoice numbers stay short and sequential, separate from the keys.
- Gap-free numbers, where required, use `UPDATE ... RETURNING` as in Soker.
