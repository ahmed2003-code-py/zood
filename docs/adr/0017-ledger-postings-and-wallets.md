# ADR 0017: Ledger postings, wallet provisioning and reconciliation

**Status:** Accepted, 2026-11-13
**Source:** `docs/architecture/implementation-plan.md` §3.5 and §7 B3; `docs/architecture/b3-ledger-contract.md`

## Context
B3 builds the only code that moves money. Plan §3.5 fixes the design (double entry in integer piastres, immutable entries, a unique source per transaction, a cached wallet balance changed only under a row lock, a nightly reconciliation) and leaves four choices open: how the guarantees are enforced, how a wallet comes to exist for every company without coupling tenancy to the ledger, how a statement is ordered when two API instances post to one wallet, and how a job with no principal reads every tenant's wallet under row-level security.

## Decision
1. **Guarantees live in PostgreSQL, code is the second line.** Debits = credits (with at least two entries) is a `DEFERRABLE INITIALLY DEFERRED` constraint trigger on both `ledger_transactions` and `ledger_entries`, so it is checked at commit and catches an entry added to an old transaction. Immutability is a `BEFORE UPDATE OR DELETE` (and `TRUNCATE`) trigger that refuses every role, the owner included, on top of the missing grants. The cached balance has `CHECK (balance_piastres >= 0)`. `(source_type, source_id)` is unique. The Java `Posting` validates the same rules before the first `INSERT`, and the posting engine pre-checks the duplicate source after taking the wallet lock so the common duplicate is refused without aborting the caller's transaction.
2. **Wallet provisioning by a synchronous domain event.** `tenancy` publishes `CompanyCreated` inside the onboarding transaction; the ledger's `@EventListener` (`Propagation.MANDATORY`) opens the account and wallet rows. Tenancy stays unaware of the ledger; a company without a wallet never commits. V6 backfills existing companies. A database trigger on `companies` was rejected because it would hide a money-related row creation inside another module's table; lazy creation on first read was rejected because a company scope may not insert wallets under RLS and every reader would have to handle a missing wallet. `MISSING_WALLET` from the reconciliation job is the safety net.
3. **Statement order is a database sequence, not the id.** `ledger_entries.seq` is `GENERATED ALWAYS AS IDENTITY`. Entries of one wallet are inserted under that wallet's lock, so for one wallet the sequence is exactly the order of its running balance, whatever the clocks of two instances say; UUIDv7 ids generated on different machines could not promise that. The statement orders and pages by `seq`, and each wallet entry stores `balance_after_piastres` (plan §5.2: running balance, no recompute).
4. **Reconciliation is a `SECURITY DEFINER` function under an advisory lock.** The nightly job has no principal and so no scope; rather than overriding the scope from Java, it calls `ledger_reconcile(...)`, which runs as the owner, takes `pg_try_advisory_xact_lock` (ADR 0011: one instance runs it), compares every cached balance with its ledger in one statement (one snapshot, so a concurrent posting cannot show as a mismatch), and writes the run, the findings and the audit row itself. The Super Admin's run-now calls the same function. The runtime role has only `SELECT` on the reconciliation tables.
5. **`ADJUSTMENT` is a reserved source type**, for the Super Admin correction endpoint of B6 (two-person rule). B3 has no endpoint for it; the B3 tests use it to debit wallets before fuelings exist.
6. **A bank reference belongs to at most one live top-up, platform-wide.** The normalised key (trim, upper case, no spaces) has a partial unique index over `PENDING` and `CONFIRMED` rows. Global rather than per company, because the guard exists to stop one transfer crediting twice and a collision between two banks' reference formats is the rarer failure; a rejected or cancelled request frees its reference.

## Consequences
- B4 posts a fueling with `ledger.post(...)` inside its own transaction and inherits every guarantee; it must lock the wallet first (`lockWallet`), which is the order plan §3.4 already prescribes.
- B5's offline sync cannot push a wallet below zero while the `CHECK` stands: it needs either a relaxing migration plus an alert, or an overdraft receivable account. This is tied to the open business question of who bears offline losses.
- A second `CompanyCreated` listener (for example a default price list or notification settings) costs one method; no outbox is needed for work that must commit with the company.
- The reconciliation function is PL/pgSQL on the money path; it is short, read-only on money tables, and tested with a deliberately corrupted cache.
- `uuidv7()` from PostgreSQL 18 is used inside V6 and `ledger_reconcile`; the project pins PostgreSQL 18 (ADR 0013, ADR 0016).
