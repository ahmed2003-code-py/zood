# Phase B3 summary: ledger and wallet (backend)

**Date:** 2026-11-13 · **Branch:** `develop` · **Contract:** `docs/architecture/b3-ledger-contract.md` · **ADR:** 0017
**Scope of this summary:** the API, and the web screens for the wallet, top-ups and reconciliation (see "Web" under Results).

## What was done

### Schema (`V6__ledger_and_wallets.sql`)

- `ledger_accounts`, `ledger_transactions`, `ledger_entries` (integer piastres, append only), `company_wallets` (cached balance, `CHECK >= 0`), `topup_requests`, `reconciliation_runs`, `reconciliation_findings`.
- Guarantees given by the database, not by code: `(source_type, source_id)` unique; debits = credits with at least two entries, checked at commit by deferred constraint triggers on both the transaction and the entries; `UPDATE`, `DELETE` and `TRUNCATE` of ledger rows refused for every role (owner included) on top of the missing grants; an entry's company must be its account's company; one bank reference per live top-up, platform-wide; a confirmed top-up is exactly one that posted.
- Row-level security: platform sees all; a company sees its own wallet, entries, transactions and top-ups, may insert only `PENDING` requests for itself and may change them only to `CANCELLED`; an operator sees none of it; the reconciliation tables are read-only for the runtime role (the definer function writes them).
- `platform:bank` opened; a wallet backfilled for every existing company.
- `ledger_reconcile(...)`: the comparison of every cached balance with its ledger, as a `SECURITY DEFINER` function under an advisory lock, one snapshot, writing its own run, findings and audit row.

### `ledger` module

- `Ledger` (public API, `Propagation.MANDATORY`): `lockWallet`, `post`. The only code that moves money. Locks wallets in ascending company id, refuses a duplicate source (`409 ALREADY_POSTED`) and a debit below zero (`409 INSUFFICIENT_BALANCE`), stores the running balance on each wallet entry, and on a downward crossing of the company's threshold writes `WALLET_LOW_BALANCE` to the audit log and publishes `WalletLowBalance` in the same transaction (the B4 alerts module's hook).
- Wallets: opened by a synchronous `@EventListener` on tenancy's new `CompanyCreated` event, in the onboarding transaction; the wallet view with `lowBalance`; the statement, newest first with the running balance, paged by the entries' database sequence.
- Top-ups: request (Fleet Manager or Accountant), cancel while pending, Ops confirm (with the reference as the statement shows it) or reject with a reason, and Ops direct credit with a bank reference (PRD §6.3 "Credit Wallet"), all audited in the same transaction. Reference normalised (trim, upper case, no spaces).
- Reconciliation: nightly at 02:30 Africa/Cairo, Super Admin run-now, Ops reads of runs and findings (`BALANCE_MISMATCH`, `MISSING_WALLET`).
- 15 endpoints under `/api/v1/company/...` and `/api/v1/ops/...`, three new permissions (`TOPUP_REQUEST`, `WALLET_CREDIT`, `RECONCILIATION_RUN`), every endpoint in `AuthorizationMatrixTests`.

### Changes outside the module

- `tenancy`: `CompanyCreated` event published inside `Companies.create`; `CompanyDirectory.CompanyRef` gains `lowBalanceThresholdPiastres`.
- `platform/security/Permission`: the three permissions, role table updated deliberately (Ops gets `WALLET_CREDIT`, Super Admin everything but the company and station reads and `TOPUP_REQUEST`).
- Tests: `IdentityTestSupport.seedCompany()` now opens the wallet too (a company without one is no longer a valid state); `NonSuperuserOwnerTests` lists the seven new RLS tables; `support/Concurrently` race helper.
- OpenAPI snapshot and `apps/web/src/api/generated/schema.d.ts` regenerated. No web screen touched.

### Who built it

The backend was written by Fable (`zawed-deep`) until a network error at Anthropic's edge stopped it twice; Opus took over, ran the tests and fixed what they found:
- **The balance trigger failed every posting** (`record "new" has no field "transaction_id"`): one PL/pgSQL function served triggers on two tables, and a `CASE` that names `NEW.transaction_id` cannot be planned for the table that has no such column. Rewritten as separate `IF` branches.
- **Opening a station payable after a concurrent insert would have aborted the payment** (caught a duplicate-key error, then queried again; PostgreSQL aborts the transaction on the failed insert). Now `INSERT … ON CONFLICT DO NOTHING`. Not reachable until B4, fixed before it is.
- A test helper read `sum(bigint)` (a `numeric`) as a `Long`.

**The Fable security review of B3 has not run yet** (Fable unavailable). It must run before B3 is called closed.

### Web (`apps/web`, http mode)

- Company portal: a wallet page with the balance, the low-balance warning, reporting a bank transfer, its requests (withdraw while pending) and the statement with the running balance.
- Ops: the top-up queue (confirm with the reference from the bank statement, or reject with a reason the company sees), a wallet section and a direct credit on the company page, and a reconciliation page (runs, differences, run now for a Super Admin).

## Decisions taken (and why)

| Decision | Why |
|---|---|
| Both company roles may request a top-up; only Ops credits | PRD §4.6 (company finance team notifies Ops), §6.2 (wallet top-up is a Fleet Panel ticket), §3 (Accountant barred from configuration actions, not from reporting a transfer; Ops "recharge corporate wallets"). **Owner to confirm.** |
| Ops direct credit exists | PRD §6.3 lists a "Credit Wallet action" on the company profile and "initial wallet balance" at onboarding. It writes the same `topup_requests` row (status `CONFIRMED`, `requestedBy` null) so one history, one reference guard. |
| Bank reference unique platform-wide over pending and confirmed requests | The guard exists to stop one transfer crediting twice; a collision between two banks' formats is rarer and Ops can resolve it by rejecting the wrong claim. |
| Confirm may correct the reference | Companies mistype; the statement's reference is what reconciles with the bank. Both are audited. |
| Wallet opened by a synchronous `CompanyCreated` event, not a trigger or lazy creation | Tenancy stays unaware of the ledger; the wallet commits with the company; nothing money-related hides in a trigger on another module's table (ADR 0017). |
| Statement ordered by a database sequence, running balance stored | Insert order under the wallet lock is the true balance order across instances; no recompute (plan §5.2). |
| Reconciliation as a `SECURITY DEFINER` function with `pg_try_advisory_xact_lock` | The job has no principal; one statement means one snapshot; the same function serves the nightly job and run-now; V3's "narrow door" pattern. No Java scope override. |
| `ADJUSTMENT` reserved, no endpoint | B6's two-person correction; B3's tests use it to debit wallets before fuelings exist. |
| Low balance: audit row + in-transaction event, no outbox | Minimal, as asked; B4 decides between a same-transaction hard alert and after-commit notifications. |
| Reconciliation findings are insert-only, no resolution fields | Resolution belongs to the cases module (B6). |

## Open questions for the owner

1. **Who may request a top-up?** Implemented: Fleet Manager and Accountant. If the Accountant must stay strictly read-only, remove `TOPUP_REQUEST` from `Role.ACCOUNTANT` in `Permission.java`; nothing else changes.
2. **Offline negative balances (B5).** The wallet cannot go below zero (`CHECK`). An offline capture that overspends must be committed (PRD §4.7). Either the constraint is relaxed by a later migration with an alert, or the shortfall posts to an overdraft receivable. This is the "who bears offline losses" question in `docs/demo/overnight-decisions.md`.
3. **Platform fee legs** (plan §3.5): not modelled until the commercial model is decided.
