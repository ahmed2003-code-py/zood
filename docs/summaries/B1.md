# Phase B1 summary: Identity and access

**Date:** 2026-11-13 · **Branch:** `develop` (not committed yet) · **Contract:** `docs/architecture/b1-identity-contract.md`

## What was done

### API (`apps/api`)

- **Schema** (`V2__identity.sql`, `V3__runtime_role_and_rls.sql`): users, sessions, MFA challenges, and an append-only audit log.
- **Database role and RLS:**
  - The application never runs as the database owner: every pooled connection switches to the `NOLOGIN` role `zawed_app`.
  - `zawed_app` cannot `DELETE` users or sessions, cannot update or delete the audit log, and cannot `TRUNCATE` anything.
  - Row-level security on `users` and `audit_log`. The scope is set for each transaction in one place (`ScopedTransactionManager`).
  - The sign-in path, which has no scope yet, goes through narrow `SECURITY DEFINER` functions instead of switching RLS off.
- **Passwords:** Argon2id with OWASP's parameters.
  - Constant-time sign-in: an unknown email, a wrong password and the wrong door look identical, after a full hash check.
  - Lockout after 5 wrong passwords for 15 minutes.
  - Policy: 12–128 characters, and must not contain the email.
- **Tokens and sessions:**
  - Access token: HS256 JWT, 15 minutes, algorithm pinned, issuer and claims checked.
  - **The session row is checked on every request**: logout, suspension or revocation takes effect at the next request.
  - Refresh token: random, stored only as SHA-256, rotated on every use by compare-and-swap.
  - 60-second race window. Reuse of an old token after that ends the whole session.
- **Cookies:**
  - Refresh cookie: `HttpOnly`, `SameSite=Strict`, `Secure` when deployed, path-scoped.
  - A separate cookie and door for the Super Admin.
  - Refresh and logout also require our `Origin` and the `X-Zawed-Client` header.
- **MFA (TOTP):**
  - Implemented in-house and tested against the RFC 6238 vectors.
  - Required for Ops and Super Admin, with enrolment forced at first sign-in.
  - A code can be used only once.
  - Challenges are single-use, short-lived and limited to 5 attempts.
  - Secrets are encrypted with AES-256-GCM and bound to their user, so a copied ciphertext does not decrypt in another row.
- **Permissions as code:** a `Permission` enum, the typed annotation `@RequiresPermission`, and one role→permission table.
- **User management:**
  - Create users with a temporary password shown once, and a forced change at first sign-in.
  - Reset password, unlock, suspend or deactivate (with a mandatory reason), reset MFA.
  - Self-change refused; the last active Super Admin is protected.
  - Ops sees only company and station users: a platform user does not exist to Ops (404).
- **Audit:** every sign-in, failure, lockout, MFA event, password change, session end and admin action is recorded in the same transaction, with the request id and a truncated IP. Read through `GET /admin/audit`.
- **Rate limiting:**
  - Sign-in: 10 per minute per address and 10 per 15 minutes per email.
  - Refresh: 30 per minute.
  - Signed-in users: 300 per minute.
  - Password change: 10 per 15 minutes.
  - All in memory, behind an interface so Redis can replace it.
- **First Super Admin:** a one-time bootstrap with `ZAWED_BOOTSTRAP_TOKEN`, compared in constant time and serialised with a lock. The endpoint answers 404 once a Super Admin exists.
- **Configuration:** a deployed instance refuses to start with a weak or committed secret, a data key that is not 32 bytes, or cookies without `Secure`.

### Web (`apps/web`)

- **Session:**
  - The access token is held in memory only, never in browser storage.
  - Refresh is automatic and single-flight; one retry after a 401.
  - Proactive refresh one minute before expiry.
  - Signing out in one tab signs out every tab.
- **Screens, in Arabic and English, light and dark:** sign-in, the admin sign-in door, the second-factor code, MFA enrolment (QR code plus a key to copy), forced password change, and "this area is not for your account".
- **Guards:**
  - The company, station and ops portals require sign-in and the right role.
  - `next` accepts only paths inside the app, so a crafted link cannot redirect elsewhere.
  - The demo (`mock` mode) still opens without sign-in.
- **The account menu** shows the real user and signs out through the API.
- **One origin in production:** the web image (Caddy) serves the app and proxies `/api` to the API over the private network.
  - It sets HSTS and a strict CSP (`script-src 'self'`); the inline pre-paint script moved to a file for this.
- **Types** come from the API's OpenAPI description; a compile-time check keeps the sign-in result in step.
- **A design-system fix:** a left-to-right field inside an Arabic page now places its icons by its own direction.

## How to run and test

```bash
cd apps/api && ./mvnw verify      # 103 tests on a real PostgreSQL
cd apps/web && npm run check      # 171 tests, typecheck, lint
```

## Results on 2026-11-13

| Check | Result |
|---|---|
| API | 103 tests, 0 failures. Includes `AuthorizationMatrixTests`: every endpoint × every role against a hand-written table. |
| RLS | Proven as `zawed_app`: another company's users are invisible even by id; writing into another scope is refused; the audit log cannot be changed; the scope does not leak to the next transaction on the same connection. |
| Web | 171 tests: refresh, retry, single-flight, sign-out, safe `next`. |
| Browser walk-through against the local API | 11 of 12 checks passed; the one failure was the browser logging the deliberate wrong-password 401. Covered: Arabic sign-in, wrong password, forced password change, landing in the portal, no token in storage, `HttpOnly` + `Strict` cookie, the session surviving a reload, the no-access page; Ops in English Dark enrolling a TOTP from the QR, changing the password, landing in /ops, and sign-out. |
| E2E of the demo (mock mode) | 51 passed |

## Deviations from the contract

Recorded in §7 of the contract:
- the per-email limit is 10 per 15 minutes;
- three new error codes: `SELF_CHANGE_NOT_ALLOWED`, `SCOPE_MISMATCH`, `INVALID_CURSOR`.
